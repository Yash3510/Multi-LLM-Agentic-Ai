# The evidence ledger

## What changed

Backend slice 2, in small commits on `4ce-core` (`6c4f85f` to `7d63d83` are the code and tests; the docs commits follow them): the evidence ledger of master plan §7.16.

- **`core/ledger` (new):** one insert-only, hash-chained list of entries per organisation, counting from 1, with the fields of Appendix B. `chain.py`, `checkpoints.py` and `verify.py` use only the standard library and `cryptography`, so the verifier can later run without a database. `make_entry` accepts exactly one form per value. `store.py` takes numbers under a lock on a per-organisation head row (`ledger_heads`), so parallel writers queue and a rolled-back action takes its number back.
- **Signed checkpoints:** an Ed25519 signature over the chain head, recorded as the next entry (type `checkpoint`) and saved as a file to keep off the machine. The key is a PEM file created by `just ledger keygen`, owner-only, never overwritten.
- **The verifier:** reports `altered`, `broken_link`, `missing`, `out_of_order`, `wrong_org`, `bad_checkpoint`, `checkpoint_mismatch`, `truncated` and `unreadable`. Without the public key signatures count as unchecked and the command exits 2, never 0. Rows changed in the database are reported, never a crash.
- **`core/db`:** `org_of(session)` and `org_isolation_sql(table, privileges=…)`, so the ledger grants the app role less than other tables.
- **`apps/server`:** migration `0004` (the two tables; insert-only triggers on both engines, TRUNCATE too on PostgreSQL; `SELECT, INSERT` on entries and `SELECT, INSERT, UPDATE` on heads for the app role), the `ledger keygen`, `checkpoint` and `verify` commands (`just ledger …`), `FOURCE_LEDGER_KEY_FILE`, and a start-up check: on PostgreSQL the server connects, and refuses to start if its role is a superuser or has `BYPASSRLS`.
- **`core/identity`:** every identity action writes a ledger entry in its own transaction: user creation, sign-in success, every sign-in failure (committed before the error is raised), lockout and sign-out. An unknown email is kept only as a keyed hash (HMAC-SHA256, key derived from `FOURCE_SECRET_KEY`).
- **Review rounds on the commands** changed their behaviour: exit 0 says plainly when the chain's length is not proven and when entries after the last checkpoint are uncovered; an explicit `--checkpoints` folder that is missing, or any unreadable checkpoint, key or folder, is exit 1 and never "no checkpoints"; a checkpoint file is never overwritten (the entry is still recorded, the JSON printed, exit 1).
- **Docs (this entry's commits):** the new [ledger page](../../../architecture/ledger.md); [identity](../../../architecture/identity.md) gained a Ledger section; [database](../../../architecture/database.md), [API](../../../architecture/api.md), [repository](../../../architecture/repository.md), [licences](../../../architecture/licences.md) and the [overview](../../../architecture/overview.md) are brought up to date; [state](../../../state.md) records what works and what comes next; [ADR-0014](../../../adr/0014-ledger-with-signed-checkpoints.md) records that a scheduled job may sign checkpoints too.

## Why

AGENTS.md §7 says every new action writes a ledger entry, and the product's promise is proof: a decision's record must show if it was edited, removed, reordered or cut. Doing it now, under identity, means every later action package writes its entries from the start. Only a checkpoint kept outside the database can prove the chain's length, so the commands refuse to let a clean exit pass for that proof.

## Decisions

[ADR-0014](../../../adr/0014-ledger-with-signed-checkpoints.md) (the ledger) and [ADR-0039](../../../adr/0039-every-action-writes-a-ledger-entry.md) (every action writes an entry), both proposed for R1 to accept. Decided by the project lead on 2026-10-24: an unknown sign-in email is kept only as a keyed hash; a scheduled job may sign checkpoints once the job queue lands (WP-F-07), while people can still run `ledger checkpoint`; the server refuses to start on PostgreSQL as a superuser or `BYPASSRLS` role. This work lands on `4ce-core` directly, as in slice 1.

## Known limits and follow-ups

Issues aren't open yet (the GitHub project isn't set up); each item becomes one.

- **The table owner or a superuser between checkpoints** can disable a trigger and cut the newest entries unseen; only a checkpoint kept outside the database shows it.
- **SQLite's `INSERT OR REPLACE`** gets past the insert-only triggers on the development engine; PostgreSQL has no REPLACE and the app role has no UPDATE.
- **No key rotation yet.**
- **No scheduled checkpoints;** they wait for the job queue (WP-F-07).
- **A SQLite batch migration that rebuilds `ledger_entries` must recreate its triggers.**
- **PostgreSQL from a Windows host is untested.**
- **Three checks not run locally** (item 5 above), pending the project lead.
- **Export, QR codes and evidence packs** are not built.
