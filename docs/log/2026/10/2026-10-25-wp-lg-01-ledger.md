# The evidence ledger

## What changed

Backend slice 2, in small commits on `4ce-core` (`6c4f85f` to `7d63d83` are the code and tests; the docs commits follow them): the evidence ledger of master plan §7.16.

- **`core/ledger` (new):** one insert-only, hash-chained list of entries per organisation, counting from 1, with the fields of Appendix B. `chain.py`, `checkpoints.py` and `verify.py` use only the standard library and `cryptography`, so the verifier can later run without a database. `make_entry` accepts exactly one form per value. `store.py` takes numbers under a lock on a per-organisation head row (`ledger_heads`), so parallel writers queue and a rolled-back action takes its number back.
- **Signed checkpoints:** an Ed25519 signature over the chain head, recorded as the next entry (type `checkpoint`) and saved as a file to keep off the machine. The key is a PEM file created by `just ledger keygen`, never overwritten; the private key is owner-only (mode 0600) on Linux and macOS, and on Windows it takes the folder's permissions, so keep the data folder private.
- **The verifier:** reports `altered`, `broken_link`, `missing`, `out_of_order`, `wrong_org`, `bad_checkpoint`, `checkpoint_mismatch`, `truncated` and `unreadable`. Without the public key signatures count as unchecked: the command exits 2 when there are signatures to check and no public key at the default place; an explicit `--public-key` that is missing is exit 1, and with nothing signed a missing default key is not an error. Rows changed in the database are reported, never a crash.
- **`core/db`:** `org_of(session)` and `org_isolation_sql(table, privileges=…)`, so the ledger grants the app role less than other tables.
- **`apps/server`:** migration `0004` (the two tables; insert-only triggers on both engines, TRUNCATE too on PostgreSQL; `SELECT, INSERT` on entries and `SELECT, INSERT, UPDATE` on heads for the app role), the `ledger keygen`, `checkpoint` and `verify` commands (`just ledger …`), `FOURCE_LEDGER_KEY_FILE`, and a start-up check: on PostgreSQL the server connects, and refuses to start if its role is a superuser or has `BYPASSRLS`.
- **`core/identity`:** every identity action writes a ledger entry in its own transaction: user creation, sign-in success, every sign-in failure (committed before the error is raised), lockout and sign-out. An unknown email is kept only as a keyed hash (HMAC-SHA256, key derived from `FOURCE_SECRET_KEY`).
- **Review rounds on the commands** changed their behaviour: exit 0 says plainly when the chain's length is not proven and when entries after the last checkpoint are uncovered; an explicit `--checkpoints` folder that is missing, or any unreadable checkpoint, key or folder, is exit 1 and never "no checkpoints"; a checkpoint file is never overwritten (the entry is still recorded, the JSON printed, exit 1).
- **Docs (this entry's commits):** the new [ledger page](../../../architecture/ledger.md); [identity](../../../architecture/identity.md) gained a Ledger section; [database](../../../architecture/database.md), [API](../../../architecture/api.md), [repository](../../../architecture/repository.md), [licences](../../../architecture/licences.md) and the [overview](../../../architecture/overview.md) are brought up to date; [state](../../../state.md) records what works and what comes next; [ADR-0014](../../../adr/0014-ledger-with-signed-checkpoints.md) records that a scheduled job may sign checkpoints too.

## Why

AGENTS.md §7 says every new action writes a ledger entry, and the product's promise is proof: a decision's record must show if it was edited, removed, reordered or cut. Doing it now, under identity, means every later action package writes its entries from the start. Only a checkpoint kept outside the database can prove the chain's length, so the commands refuse to let a clean exit pass for that proof.

## Known limits and follow-ups

Issues aren't open yet (the GitHub project isn't set up); each item becomes one.

- **Failed sign-ins grow the ledger without bound** until sign-in rate limits land (WP-F-11): the ledger is insert-only, so rows can't be pruned without breaking verification.
- **The table owner or a superuser between checkpoints** can disable a trigger and cut the newest entries unseen; only a checkpoint kept outside the database shows it.
- **SQLite's `INSERT OR REPLACE`** gets past the insert-only triggers on the development engine; PostgreSQL has no REPLACE and the app role has no UPDATE.
- **No key rotation yet.**
- **No scheduled checkpoints;** they wait for the job queue (WP-F-07).
- **A SQLite batch migration that rebuilds `ledger_entries` must recreate its triggers.**
- **PostgreSQL from a Windows host is untested.**
- **Three checks not run locally** (item 5 above), pending the project lead.
- **Export, QR codes and evidence packs** are not built.

## Final review fixes

The whole-slice review of the ledger found five important problems and a list of smaller ones; all were fixed in one wave on `4ce-core` (base `75c8dff`), each logic change with a failing test first.

- **The verifier is pure again.** `UnusableKey` had moved into a module that imports `fource.common`, so the checkpoint code pulled in pydantic. It now lives in `checkpoints.py`, and an import-linter contract forbids `fource.common`, `fource.db`, SQLAlchemy and pydantic in `chain`, `checkpoints` and `verify`. The contract was shown to fail first: with the old code `just imports` reported `fource.ledger.checkpoints -> fource.ledger.errors -> fource.common -> … -> pydantic`.
- **An undecodable first row is reported, not raised.** The stream was opened outside the guard, and SQLAlchemy fetches the first batch while opening it, so `ledger verify` printed a traceback. Opening is now inside the guard (the entry is reported as `unreadable`, from entry 1); a missing table is still raised so the commands can say the database isn't set up. A real SQLite test corrupts entry 1 and entry 2.
- **Sign-out no longer reports success for a token that still works.** The savepoint covered the revocation and the ledger entry, and an integrity error from either was swallowed. Now only a lost race (the token really is revoked afterwards) counts as success; a clash in the ledger raises.
- **A missing table is "not set up" on PostgreSQL too.** `ledger checkpoint` and `ledger verify` caught only `OperationalError`; PostgreSQL raises `ProgrammingError` (state 42P01). Both commands now catch both, print the not-set-up line for a missing table, and for any other database error print `Could not read the database: <ErrorClass>.` (no traceback, no URL). Sign-in on a database migrated only to `0003` answered 500 because sign-in writes the ledger; it now answers 503 `setup_incomplete`. The check lives in one place, `fource.db.table_missing` (in `core/db` rather than the server, because the ledger reader needs it too).
- **The server also refuses to start as the owner of the ledger tables** (or a member of the owning role), not only a superuser or `BYPASSRLS` role: on managed PostgreSQL the owner is usually neither, yet could disable the trigger or turn off forced row-level security.
- **Smaller fixes:** refs that are not an object (a list of pairs, which `dict()` turns back into the original) are reported `altered`; `ledger verify` prints `Checked against key <id>.` so an auditor can compare it with their own copy of the public key; the insert grant of the app role is now tested, and so are 20 concurrent writers for the first entries of an empty ledger (PostgreSQL), and an inactive user's failed sign-in entry (SQLite); comments say the column select bypasses the session's confinement and that `sign_in` commits on every failure. Docs: the key permissions per platform, the true exit-2 rule, the owner can disable the trigger, failed sign-ins grow the ledger without bound, `ledger_heads` is under row-level security, the ADR table in number order, and `just migrate` after pulling.
